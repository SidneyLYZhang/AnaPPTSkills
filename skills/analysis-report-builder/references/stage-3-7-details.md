# 阶段 3-7 详细执行指引

> 阶段 0-2 及四个决策门已在 SKILL.md 中完整描述。本文件为阶段 3-7 的详细参考，在相应阶段到达时读取。

## 阶段 3：数据准备与确认

**流程**：数据差距评估 → 数据需求文件 → 数据质量核对 → 口径确认

1. **数据差距说明**（模板 `assets/templates/03-数据差距说明.md`）：已有数据清单 vs 框架所需数据，标注缺失项的意义与紧急程度。gap 太多时，用户可基于此反向推进数据团队补充。
2. **数据需求文件**（模板 `assets/templates/04-数据需求文件.md`）：描述完成每个分析需求需要哪些数据支撑，以及数据准备方式（给数据团队/用户的取数需求文档）。
3. **数据质量报告与口径确认**（模板 `assets/templates/05-数据质量报告与口径确认.md`）：核对数据字典、清洗留痕（每次清洗记录原因与影响）、确认口径、出具质量评估。

**完成条件**：质量问题有清单且标注"能用但打折"；口径有用户确认记录；数据版本快照可复现。若数据由用户提供文件，先读文件再核对；若用户暂无数据，降级为"外部数据 + 访谈信息"，并在报告中如实声明局限。

## 阶段 4：外部信息 + 初步验证 + 大纲

1. 收集外部基准（每条标注来源与时效，需联网搜索）
2. 用已有数据跑一轮初步结果，验证阶段 2 的假设。结果解读按 `references/data-interpretation-guide.md` 的四层递进（L1 事实→L2 对比→L3 解释→L4 启示）——无基准不下好坏判断，无归因证据不下因果措辞，证据不足时降级为"相关/伴随/可能源于"。
3. 写文字版大纲（金字塔结构，结论先行）

产出物：《分析大纲 v0.5》（模板 `assets/templates/06-分析大纲.md`），含外部信息清单与局限声明。

**完成条件**：每个发现都有参照系；假设要么被初步验证、要么被推翻并修正——被推翻的假设必须回到阶段 2 向用户说明并调整框架。

## 阶段 5：文字版报告 v1.0

**目标**：把 06 号大纲扩写为可交付的文字报告，让目标受众读完能做决策。

**前置读取**：动笔前必须加载 `references/report-writing-llm-spec.md`（写作阶段 LLM 指引规约 v2）。该规约是本阶段权威，定义输入清单与权威层级、硬约束、骨架继承、边界/论证/表达规约、特殊情形与评审回路；本节只给执行骨架，细则以规约为准。

### 三步生成（禁止单次成稿）

1. **骨架继承与校验**——06 号大纲即骨架，不另起炉灶。三项校验：必要结论覆盖矩阵（`success_criteria.required_conclusions` × 大纲结论，无孤儿）；被推翻假设的下游结论已移除或修正；每个结论的参照系（环比/同比/预算/外部基准）完备。骨架层面的增删结论、改章节顺序不在写作阶段权限内，须回到阶段 4 并告知用户。
   - *完成*：校验记录 + 覆盖矩阵就位，三项全过。
2. **数字台账**——列出全文将用的全部数字（数值/单位/口径出处/来源编号/计划出现位置）。成文后逐项回查：正文与台账一致？台账数字全部用上？正文出现而台账没有的数字 = 幻觉信号，立即核查。
   - *完成*：台账完整，每个数字可回溯到阶段 3 数据快照或 06 号外部信息清单。
3. **分章撰写 + 终稿通读**——逐章写，以骨架与台账为基准。数据/统计/归因段落的解读措辞与陷阱检查按 `references/data-interpretation-guide.md`：统计三件套（点估计+置信区间+效应量）同报、p 值转译业务量级、归因结论用贡献度话术且各因素合计覆盖总变动、触发"占比变化/合并分组/小样本比率/相关关系"信号词时查对应陷阱。终稿通读只改三类问题：数字一致性、术语一致性（对 05 号签字口径）、前后论断矛盾。最后执行模板文末自检清单 + 规约第一节硬约束复查。
   - *完成*：报告 v1.0 成稿，自检清单全绿。

### 产出物

《分析报告 v1.0》（模板 `assets/templates/07-报告模板.md`）；管理层版必须附一页纸摘要。结构、图表三要素、篇幅配额、确定性三级表达、禁用词等细则见规约第四、五节与模板文首生成指令。

### 阶段完成条件

- **建议可执行**——每条建议指明谁、做什么、何时、预期效果（模板建议表"依据"列已填）。
- **数据可追溯**——每个数字可回溯到阶段 3 数据快照或 06 号外部信息清单。
- **禁区零越界**——`report.yml compliance` 的 `cannot_quote` / `cannot_conclude` 全文（含附录、图表注释）零出现。
- **必要结论全落点**——`success_criteria.required_conclusions` 每条在报告中有明确落点。

## 决策门 D：初稿评审

**评审**：阶段 5 完成条件全绿后，启动独立评审 prompt（规约第八节）：以受众立场挑剔阅读，只输出问题清单——存疑论断及原因、数字/术语/逻辑前后不一致、"看起来正确但无信息量"的句子；不重写。

**回路**：问题清单回喂写作 LLM 逐条修订；修订稿连同评审记录与自查清单（数字一致性、来源可追溯、建议可执行、语言符合受众矩阵）提交用户。未过则回到阶段 5 修订并记录版本变更。

## 阶段 6：PPT

**设计原则**：一页一观点、标题即结论、图表重绘（不截图贴表）、配讲稿备注；按决策门 A 确认的受众选版本（决策场景 10-20 页）。

### 6.1 PPT 技能检测与选择

扫描已安装的 PPT 技能（`dashi-ppt`、`slides` 等），多个则让用户选，默认推荐 `dashi-ppt`。未检测到时提示用户安装（按 dashi-ppt SKILL.md 指引）；用户暂不安装则降级为"带分页结构的完整演示脚本"（每页标题、要点、图表说明、讲稿），并告知无法直接生成可视化 PPT 的局限。

### 6.2 输入准备

调用 PPT 技能前，整理两类输入：

1. **文字版报告**：阶段 5 已通过决策门 D 确认的《分析报告 v1.0》全文（结论先行、金字塔结构、含图表三要素与建议）。
2. **`report.yml` 关键信息**：
   - `title` / `subtitle`——PPT 封面标题
   - `audience`——受众版本（管理层 / 执行层 / 外部客户），决定语言深度与篇幅
   - `delivery.ppt_pages`——目标页数（决策场景 10-20 页）
   - `delivery.theme`——主题偏好（传入 dashi-ppt 的视觉主题选择）
   - `success_criteria.required_conclusions`——必须呈现的核心结论，确保不漏

### 6.3 调用 PPT 技能

将 6.2 的输入传入所选 PPT 技能，明确告知：基于报告内容组稿，按受众版本调整语言，图表需重绘而非贴截图。主题选择、在线编辑、导出等具体流程按该技能 SKILL.md 执行。

### 6.4 机器与样式校验

dashi-ppt 渲染完成后，主 agent 执行秒级校验（5 项）：

- `props:safe` / `validate:goal-spec` / `validate:swiss` / `validate:goal-copy` 已全绿。
- 一页一观点、标题即结论。
- 图表为重绘版式，非截图贴表。
- 每页配讲稿备注。
- 页数与 `report.yml.delivery.ppt_pages` 及受众版本匹配。

未过则回到 6.3 修订 props 或换 layout。通过后进入 6.5 对账——机器校验只保证技术基线，不保证信息完整。

### 6.5 报告↔PPT 对账（subagent 核验回路）

**目标**：以《分析报告 v1.0》为账本，对生成的 PPT 做信息维度对账；对账不过不交付。由独立 subagent 执行，避免主 agent「既生成又自查」的盲区。

**对账锚点**（主 agent 在启动 subagent 前整理，作为 subagent 输入）：

- **必要结论清单**：`report.yml.success_criteria.required_conclusions`，每条标注报告中的落点章节。
- **章节骨架**：报告一级/二级标题 + 每章核心结论（一段一论点）。
- **数字台账**：从阶段 5 复用，每条数字附「计划出现位置」；只取必要结论所依赖的核心数字，不核对全文数字。
- **禁区清单**：`report.yml.compliance.cannot_quote` / `cannot_conclude`。

**对账 subagent prompt**（独立会话执行，不共享主 agent 上下文）：

> 你是报告交付的对账员。账本 = 《分析报告 v1.0》；对账对象 = 已渲染的 PPT（`goal.json` + `ppt/index.html`）。
> 输入：对账锚点四项 + PPT 全量可见文案（每页标题、正文、图表 insight、讲稿备注）。
> 只做四件事，不重写 PPT，不评价视觉：
> 1. **结论覆盖矩阵**：每条必要结论是否有 PPT 页承载？无承载页 = 缺失。
> 2. **章节覆盖**：报告每章至少 1 页承载？整章缺失或仅降级为单点提及 = 缺失。
> 3. **数字一致性**：核心数字在 PPT 中是否出现且与台账一致？不一致或缺失 = 不一致。
> 4. **禁区扫描**：PPT 全量文案（含备注）是否出现 `cannot_quote` / `cannot_conclude`？任何越界 = 越界。
> 输出《对账问题清单》，每条指明：类型（缺失/不一致/越界/重复）、所在 PPT 页或「无承载页」、报告侧出处、修订动作（补页/换 layout/改 props/删）。

**修订回路**（最多 2 轮）：

1. 主 agent 将《对账问题清单》回喂 dashi-ppt：缺失用 `layout:query` 选合适 layout 补页；不一致改 props；越界删改；重复 layout 换页。
2. 重新渲染 → 重跑 `props:safe` / `validate:*` → 重启对账 subagent。
3. **终止**：对账问题清单为空；或两轮后仍残留——残留即标记「阻塞」，向用户说明未对账项，不进入 6.6。

**完成条件**：对账问题清单为空；必要结论 100% 覆盖；报告每章有 PPT 承载页；核心数字一致；禁区零越界。

### 6.6 交付

对账通过后，预览服务、在线编辑、PPTX/PDF 导出按 dashi-ppt SKILL.md 执行。更新 `_报告进度.md`：阶段 6 完成，记录对账轮次、最终页数、预览地址、是否已导出 PPTX。

**完成条件**：预览地址已交付用户；进度文件已更新；用户可自助编辑与导出；进入阶段 7。

## 阶段 7：优化与交付 + 复盘沉淀

- 电梯测试：让用户（或自述）30 秒内复述核心结论，复述不出则回阶段 6 精简。
- 评审意见分"结论质疑 / 呈现意见"两类处理：结论质疑回到相应阶段，呈现意见原地修改。
- 记录版本与变更；向用户交付复盘沉淀清单（本次可复用的模板、口径、踩坑点），询问是否沉淀入库。
