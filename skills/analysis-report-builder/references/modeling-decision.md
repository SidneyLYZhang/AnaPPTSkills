# 建模决策（决策门B）与业务化翻译

> 立场：**建模不是加分项，默认不建模，除非有明确理由。** 多数经营分析问题用描述统计 + 对比 + 归因就够；硬上模型反而拉长周期、降低可解释性。决策单必须写明"不建模的风险"，并交用户确认签字，防止事后"当时为什么没建模"的争议。

## 前置联动检查（与 report.yml）

在进入三列判断之前，必须先读取 `report.yml` 的以下字段，评估建模的可行性边界：

- `constraints.deadline`：交付截止时间是否允许建模周期？
- `objectives`：报告目标是"描述/诊断"还是"预测/优化"？
- `audience.primary`：主受众对可解释性的要求（管理层 → 强可解释，外部 → 方法透明）
- `existing_materials`：数据条件是否支持建模？

若 `deadline` 紧迫 + `objectives` 偏向描述/诊断，应直接决策"不建模"，无需进入三列判断。

## 三列判断表（三列都要过）

| 判断维度 | 不需要建模 | 需要建模 |
|---|---|---|
| 目标类型 | 描述"是什么"、诊断"为什么"（对比/归因/漏斗可答） | 预测"会怎样"、优化"怎么做" |
| 数据条件 | 样本不足、无标签、数据质量差 | 有效样本足够（分类/回归一般 ≥ 几百条，经验值，按问题复杂度评估）、标签可得 |
| 交付约束 | 时间紧、管理层要求强可解释 | 时间允许、结论用于内部决策、可接受模型复杂度 |

判断时逐列对照并写明证据，不允许凭感觉。

## 常见误用

1. **为了显得高级而建模**：回归能答的问题不要上机器学习。
2. **样本量不足硬做**：几百条以下的数据做复杂模型，方差远大于信号；此时改用规则 + 敏感性分析并如实说明。
3. **把相关性当因果**：模型发现的相关不能直接写成"X 导致 Y"；需要业务机制佐证或明确降级为关联表述。
4. **跳过验证直接交付**：任何模型都要有训练/验证分割或时序回测，指标与基线对比（不建模的朴素基线）。

## 建模子流程（决策为"是"时）

1. **模型设计**：问题形式化（分类/回归/排序/聚类）、特征清单与可得性、基线模型先行。
2. **验证**：评估指标选择（对齐业务目标而非默认 AUC）、验证集/时序回测、误差案例分析。
3. **业务化翻译（强制最后一步）**：模型系数、特征重要性、置信区间对管理层没有意义，必须翻译成：
   - **哪些因素影响最大**（用业务语言，如"价格敏感度"而非"price_coefficient"）；
   - **影响多少**（量级 + 置信区间，用业务单位，如"每降 1 元约多带来 N 单，区间 ±M"）；
   - **建议怎么调整**（对应可操作的杠杆，并注明模型外推的边界——超出训练数据范围的调整要谨慎）。
4. 翻译结果并入阶段 5 报告，按受众矩阵决定呈现深度（管理层只见结论 + 置信度）。
