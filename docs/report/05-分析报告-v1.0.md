# 正文

## 核心结论（一页纸摘要）

**AnaPPTSkills 是一套聚焦"报告全流程管控"的 AI Agent 技能集，由两个 Skill（setup-anappt + analysis-report-builder）和一份 SOP（7 阶段 + 4 决策门）组成。它不生成 PPT 视觉，而是解决"如何从需求承接到交付一份完整报告"的流程问题——与同类 PPT 生成 Skill 形成"流程 + 视觉"的互补关系。**

业务分析人员按 README 三步即可上手，无需理解 Skill 机制。报告写作的三大痛点（需求不清就开干、流程不可控、断点难续）均有对应机制对症。项目基于 MIT License 开源，欢迎贡献。

## 第一章：AnaPPTSkills 是什么

### 1.1 一句话定位

AnaPPTSkills 是一套面向经营/咨询分析报告的 AI Agent 技能集（Skills），让 AI（大语言模型，LLM）以"分析负责人 + 数据分析师"的身份，按标准化 SOP 与用户协作完成一份分析报告——从需求承接到文字报告，再到 PPT 交付。

**关键边界**：AnaPPTSkills 是 AI Agent 技能集（Skill），不是可执行程序。每个 Skill 通过一个名为 `SKILL.md` 的声明文件告诉 AI Agent"什么意图触发、按什么原则交互、按什么步骤执行"；Agent 在对话中识别到用户意图后，按 Skill 定义的结构化流程推进。

### 1.2 不是什么（边界澄清）

AnaPPTSkills 的定位是"流程管控层"工具，以下事项不在其范围内：

- **不是 PPT 视觉生成工具**——不提供主题、版式、控件、配色等视觉能力。PPT 视觉生成由阶段 6 推荐配合的 dashi-ppt-skill 完成。
- **不是可执行程序**——不能独立运行，必须依赖 AI Agent 加载。
- **不是通用聊天 Skill**——只响应报告构建相关意图，不处理无关对话。
- **不是建模框架**——建模默认不做（详见第四章），仅在三列判断都满足时才启用。

### 1.3 两个 Skill 的分工

AnaPPTSkills 包含两个 Skill，前后依赖：

| Skill | 角色 | 定位 | 触发词示例 |
|---|---|---|---|
| `setup-anappt` | 项目初始化 | 准备工作目录、锚定 git、生成首个 commit | "初始化报告项目""新建分析项目" |
| `analysis-report-builder` | 报告构建主流程 | 按 7 阶段 + 4 决策门协作产出报告 | "做一份分析报告""经营分析""按 SOP 走报告流程" |

`setup-anappt` 先建目录与状态文件，`analysis-report-builder` 读取并推进流程。两者缺一不可。

## 第二章：解决什么问题

### 2.1 报告写作三大痛点

写分析报告常见三类痛点（来源：README + 分析SOP）：

1. **需求不清就开干**——目标受众、决策场景、成功标准没对齐，返工率高。
2. **流程不可控**——没有质量门，建模与否凭感觉，初稿评审流于形式。
3. **断点难续**——多轮对话后状态丢失，换个会话就得从头讲背景。

### 2.2 SOP 如何对症

AnaPPTSkills 用一份 SOP + 两个 Skill 对症三大痛点：

| 痛点 | 对症机制 | 如何起作用 |
|---|---|---|
| 需求不清就开干 | **grill 追问机制** | 阶段 0-1 反复追问直到 `report.yml` 锁定。答不出"给谁看 / 为什么现在做 / 要什么结论 / 何时交付"四问，不进入下一步。 |
| 流程不可控 | **四个决策门** | A 受众分层、B 建模评估、C 框架评审、D 初稿评审，作为质量刹车。每门必须用户确认才进入下一阶段。 |
| 断点难续 | **`_报告进度.md`** | 每步产出物写入状态文件。新会话读取后从断点继续，无需重讲背景。 |

**决策门的设计原则**：评审人与执行人不要是同一个人，否则评审形同虚设（来源：分析SOP 落地建议）。决策门 C（框架评审）与决策门 D（初稿评审）建议固定 30 分钟评审会——这是 SOP 的"刹车"，也是质量下限。决策门的详细设计与取舍见第四章 4.1。

### 2.3 适合什么场景

AnaPPTSkills 适合以下场景：

- **经营分析报告**：需要从需求承接到 PPT 交付的完整流程
- **咨询分析报告**：框架驱动、结论导向的分析
- **专题分析 / 竞品分析**：有明确决策问题、需要按读者类型调整呈现深度的报告（受众分层机制详见第四章 4.3）
- **多轮协作的报告项目**：需要断点续跑、跨会话恢复的场景

**不适合的场景**：仅需快速生成一张 PPT 视觉、无需流程管控的即时任务——此类需求直接使用 dashi-ppt-skill 或 guizang-ppt-skill 更合适。

## 第三章：如何快速上手

### 3.1 前置环境

- 一个支持 Skill 加载的 AI Agent（如 Trae、Claude Code）——即能加载并执行 Skill 的 AI 编程助手
- Node.js（用于 `npx skills add` 安装命令）——`npx` 是 Node.js 自带的命令行工具，用于一次性执行 npm 包。Node.js 安装地址：https://nodejs.org/ ；安装后在终端输入 `node -v` 能看到版本号即表示已就绪
- Git（`setup-anappt` 会锚定 git 仓库）——版本管理工具，安装地址：https://git-scm.com/

无需额外技术栈。业务分析人员无需懂 Skill 机制、无需写代码。

### 3.2 三步上手

**第一步：安装 Skill**

两种方式任选其一：

```bash
# 方式一：使用 npx skills add（推荐）
npx skills add https://github.com/sidneylyzhang/AnaPPTSkills

# 方式二：让 Agent 自主完成安装
# 在对话中直接说："请帮我安装 AnaPPTSkills https://github.com/sidneylyzhang/AnaPPTSkills 这个技能集"
```

执行完成后，`setup-anappt` 与 `analysis-report-builder` 会自动注册到 Agent 的 Skills 列表。

**第二步：初始化项目**

在对话中触发 `setup-anappt`，说出意图即可：

> "初始化报告项目"

Skill 会创建标准目录结构：

```
<目标目录>/
├── report.yml           ← 报告设定文件（阶段 0-1 填充并锁定）
├── _报告进度.md           ← 断点续跑状态文件
└── data/                ← 用户数据文件目录
```

并完成首次 git commit。

**第三步：构建报告**

触发 `analysis-report-builder`，说出意图即可：

> "做一份经营分析报告"

Skill 会读取状态文件，进入阶段 0-1 grill 追问。每阶段确认后自动推进，直到阶段 7 交付。

### 3.3 中断与续跑

- **随时可中断**：说"停""改需求""回到阶段X"立即响应并更新状态。
- **新会话续跑**：再次触发主 Skill，会读取 `_报告进度.md` 从断点继续，无需重讲背景。

## 第四章：设计理念

> 本章面向同行与 Agent 开发者，说明 AnaPPTSkills 为什么这样设计。业务分析人员可跳过本章直接看第五章。

### 4.1 质量刹车：四决策门

四决策门是 SOP 的核心设计，分别在关键节点强制用户确认：

| 决策门 | 位置 | 作用 | 未过后果 |
|---|---|---|---|
| A 受众分层 | 阶段 0-1 后 | 确认主/次受众与报告形态 | 不进入阶段 2 |
| B 建模评估 | 阶段 2 后 | 判断是否需要建模 | 不进入决策门 C |
| C 框架评审 | 决策门 B 后 | 评审框架与数据需求 | 回到阶段 2 |
| D 初稿评审 | 阶段 5 后 | 评审文字版报告 | 回到阶段 5 |

**设计取舍**：决策门会降低流程速度，但保证质量下限。第二章 2.2 已述"评审人与执行人不要是同一个人"——此处补充其落地方式：SOP 落地建议明确指出决策门 C（框架评审）与决策门 D（初稿评审）应固定 30 分钟评审会，由独立评审人把关，防止决策门流于形式。

### 4.2 默认不建模：三列判断

AnaPPTSkills 的建模决策遵循"默认不做"原则。判断依据是三列都要过：

| 判断维度 | 不需要建模 | 需要建模 |
|---|---|---|
| 目标类型 | 描述"是什么"、诊断"为什么" | 预测"会怎样"、优化"怎么做" |
| 数据条件 | 样本不足、无标签、数据质量差 | 有效样本足够、标签可得 |
| 交付约束 | 时间紧、要求强可解释 | 时间允许、可接受复杂度 |

**设计理由**：多数经营分析问题用描述统计 + 对比 + 归因就够，硬上模型反而拉长周期、降低可解释性。若建模，强制要求最后一步是"业务化翻译"——把系数、特征重要性、置信区间翻译成"哪些因素影响最大、影响多少、建议怎么调整"。

### 4.3 受众适配：一份结论按受众裁剪

AnaPPTSkills 的受众适配不是"做三份报告"，而是"一份结论、针对性呈现"：

| 维度 | 管理层 | 业务人员 | 外部人员 |
|---|---|---|---|
| 核心诉求 | 决策依据 | 操作指引 | 可信度 / 合规 |
| 篇幅 | ≤15 页 + 一页纸摘要 | 详细版 + 分场景操作建议 | 完整版 + 附录 |
| 语言 | 结论 + 影响 + 建议，少术语 | 结合业务场景，术语带解释 | 中立客观，方法透明 |
| 证据强度 | 关键证据 + 风险提示 | 详细数据 + 操作步骤 | 全部来源 + 方法论 + 局限声明 |

### 4.4 断点续跑：状态文件机制

`_报告进度.md` 是断点续跑的核心。每完成一个产出物或子步骤立即更新该文件，包含：

- 项目基本信息
- 当前进度（阶段、子步骤、问题、已完成、待讨论）
- 各阶段状态表（阶段、产出物、文件路径、状态、确认时间）
- 问题列表
- 关键决策记录
- 变更记录

新会话开始时，Skill 先检测该文件：不存在则提示先调用 `setup-anappt`；存在则读取后从断点继续。

## 第五章：与同类工具的差异

### 5.1 定位层级差异

同类 PPT 生成工具与 AnaPPTSkills 的核心差异在"定位层级"：

- **视觉生成层**：聚焦"如何把内容做成好看的 PPT"——提供主题、版式、控件、配色、设计风格。
- **流程管控层**：聚焦"如何从需求承接到交付一份完整报告"——提供 SOP、决策门、断点续跑、受众适配。

AnaPPTSkills 属于流程管控层，PPT 仅是其末段（阶段 6），且视觉生成推荐配合 dashi-ppt-skill 完成。两者是互补关系，非竞争关系。

### 5.2 对比矩阵

以下对比基于公开 README 调研（2026-08-04），用"差异点""侧重点不同"表述，不下优劣结论。

| 对比维度 | AnaPPTSkills | ppt-master | dashi-ppt-skill | guizang-ppt-skill | 通用 AI PPT（Gamma/Tome） | 传统报告 SOP |
|---|---|---|---|---|---|---|
| 定位层级 | 流程管控 | 视觉生成 | 视觉生成 | 视觉生成 | 视觉生成 | 流程管控（人工） |
| 流程可控性 | 有（7 阶段 + 4 决策门） | 无 | 无 | 无 | 无 | 有（依赖个人经验） |
| 需求追问机制 | 有（grill 追问） | 无 | 无 | 无 | 无 | 无 |
| 断点续跑 | 有（状态文件自动恢复） | 无 | 无 | 无 | 无 | 弱（靠人工文档记录） |
| 受众分层 | 有（受众矩阵） | 无 | 无 | 无 | 无 | 有（依赖经验） |
| 结论先行 | 有（金字塔结构） | 无 | 无 | 无 | 无 | 有（依赖经验） |
| 输出格式 | Markdown + PPTX（配合 dashi） | .pptx | HTML + PDF + PPTX | 单文件 HTML | 多种 | 文档 |
| 技术栈 | AI Agent + Node.js（安装） | Python | Node.js | Node.js | SaaS | 无 |
| 安装方式 | npx skills add | 克隆仓库 | npx dashi-ppt-skill | npx skills add | 注册账号 | 无 |

### 5.3 与 dashi-ppt 的互补关系

AnaPPTSkills 与 dashi-ppt-skill 是互补关系，非竞争关系：

- **AnaPPTSkills 管流程与内容**：从需求承接到文字报告，保证内容质量与流程可控。
- **dashi-ppt 管视觉**：12 套主题、1020 版式、8576 控件、浏览器编辑控制台，保证 PPT 视觉效果。

AnaPPTSkills 阶段 6 推荐配合 dashi-ppt-skill 使用——本项目聚焦内容与结论呈现，将版式与视觉打磨交给专业工具。

**与 ppt-master、guizang-ppt 的关系**：同为视觉生成层工具，与 AnaPPTSkills 无功能重叠。用户可按视觉偏好选择：
- 需要原生 PowerPoint 对象深度 → ppt-master
- 需要强设计风格 + 叙事表达 → guizang-ppt
- 需要职场通用 + 可编辑 → dashi-ppt（AnaPPTSkills 推荐）

### 5.4 与通用 AI PPT 工具、传统 SOP 的差异

- **与通用 AI PPT 工具（Gamma、Tome、ChatGPT 直接生成）的差异**：通用工具是一键生成，无流程管控、无需求追问、无断点续跑；AnaPPTSkills 是流程化协作，每个节点有质量门。
- **与传统报告 SOP 的差异**：传统 SOP 依赖个人经验，规范性、可复现性弱；AnaPPTSkills 是标准化 SOP，状态可复现、流程可复用。

## 结论与建议

### 核心结论

AnaPPTSkills 是一套聚焦"报告全流程管控"的 AI Agent 技能集，与同类 PPT 生成 Skill 形成"流程 + 视觉"的互补关系。它用 SOP + 两个 Skill 对症报告写作三大痛点，小白用户按三步可上手，设计理念核心是"质量刹车"与"默认不建模"。
