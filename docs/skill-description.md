# AnaPPTSkills 技能说明

AnaPPTSkills 是一套面向**经营 / 咨询分析报告**的 AI Agent 技能集，由两个相互配合的 Skill 组成。它们不是可执行程序，而是通过 `SKILL.md` 声明触发条件、交互原则与执行步骤，由 AI Agent（如 Trae、Claude Code）在对话中识别意图后按结构化流程推进。

| Skill | 角色 | 定位 |
|---|---|---|
| `setup-anappt` | 项目初始化 | 准备工作目录、锚定 git、生成首个 commit |
| `analysis-report-builder` | 报告构建主流程 | 按 7 阶段 + 4 决策门协作产出报告 |

两者为前后依赖关系：先 `setup-anappt` 建目录与状态文件，再由 `analysis-report-builder` 读取并推进流程。

---

## 一、`setup-anappt`——项目初始化

### 触发条件

用户说出以下任意意图时触发：

- "初始化报告项目"
- "新建分析项目"
- "开始一个新的分析报告"
- 直接点名 "setup-anappt"

### 如何使用

在对话中直接表达上述意图即可，无需参数。也可附带目录名作为参数（在当前工作目录下创建子目录）。

Skill 会按以下 5 步执行：

1. **确认目录**：无参数则用当前工作目录；有参数则以参数名为子目录名创建。
2. **锚定 git（避免嵌套仓库）**：先执行 `git rev-parse --is-inside-work-tree` 判断当前目录是否已被某 git 仓库覆盖：
   - 已覆盖 → 不再 `git init`，沿用既有仓库；
   - 未覆盖 → 在目标目录执行 `git init`。
3. **创建目录结构与文件**：
   ```
   <目标目录>/
   ├── report.yml           ← 报告设定文件（阶段 0-1 填充并锁定）
   ├── _报告进度.md           ← 断点续跑状态文件
   └── data/                ← 用户数据文件目录（空）
   ```
   两个文件分别从 `skills/setup-anappt/assets/templates/` 复制，内容保持空字段待填。
4. **首次提交**：`git add report.yml _报告进度.md data/` 并 commit "chore: 初始化分析报告项目"。
5. **完成告知**：列出已创建文件、git 仓库状态、下一步（调用 `analysis-report-builder` 开始阶段 0-1）。

### 产出物

- `report.yml`：报告设定文件，包含 title / motivation / audience / objectives / success_criteria / delivery / scope / constraints / existing_materials / reader_context / compliance / benchmark 等字段，初始全空。
- `_报告进度.md`：断点续跑状态文件，含项目基本信息、当前进度、各阶段状态表、问题列表、关键决策记录、变更记录。
- `data/`：空目录，用于后续存放用户数据。

### 使用约束

- **不允许嵌套 init**：必须先检测是否已被 git 仓库覆盖，避免在已仓库内再 `git init` 产生嵌套。
- **模板内容保持不变**：复制 `report.yml` 与 `_报告进度.md` 时内容原样复制，所有字段留空，由阶段 0-1 填充，本 Skill 不预填任何字段。
- **完成条件严格校验**：三件产出物必须真实存在于目标目录；`git rev-parse --is-inside-work-tree` 在目标目录必须返回 `true`；`git log --oneline -1` 必须显示首条 commit。
- **本 Skill 只负责初始化**：不进入需求追问、不填充 `report.yml`、不创建报告内容文件——这些由 `analysis-report-builder` 负责。

## 二、`analysis-report-builder`——报告构建主流程

### 触发条件

用户说出以下任意意图时触发：

- "做一份分析报告"
- "经营分析""业务分析""专题分析""竞品分析"
- "按 SOP 走报告流程"
- "帮我逐步构建报告"
- 中断后继续已有报告流程时再次触发

### 如何使用

#### 前置检查

新会话开始时先检测 `_报告进度.md` 与 `report.yml`：

- **不存在** → 提示用户先调用 `setup-anappt`；
- **存在** → 读取后从断点继续，或按用户要求从指定阶段重做（重做时保留上游产出物，只覆盖该阶段及之后内容）。

#### 总体流程

以"分析负责人 + 数据分析师"身份，与用户（业务对接人 + 质量评审人）协作，按 7 阶段 + 4 决策门推进：

```
阶段0-1 需求承接（grill 追问）→ report.yml
        ↓
【决策门A】受众分层与报告形态
        ↓
阶段2 分析框架与数据需求
    ├─ 判断报告类型 → 外部搜索决策 → 指标口径 → 方法 → 数据清单
    ↓
【决策门B】是否建模（默认不建模）→【决策门C】框架评审
        ↓
阶段3 数据准备 → 阶段4 外部信息+初步验证+大纲
        ↓
阶段5 文字版报告 v1.0 →【决策门D】初稿评审
        ↓
阶段6 PPT → 阶段7 优化交付 + 复盘沉淀
```

每阶段统一执行 5 个动作：(1) 说明本阶段目标；(2) 按模板产出交付物；(3) 对照完成条件自查；(4) 呈现用户确认；(5) 更新 `_报告进度.md`。

#### 各阶段要点

- **阶段 0-1 需求承接**：用 grill 追问机制生成 3-5 个高优先级问题，逐题深挖，动态填充 `report.yml`。用户模糊时主动给出 2-3 个具体选项 + 推荐理由。终止条件为 `report.yml` 全字段填充且用户确认"可以锁定"。**4 问必答**：给谁看？为什么现在做？要什么结论？何时交付？答不出任一继续追问。
- **决策门 A**：确认主/次受众与报告形态。管理层版不是业务版删减版，而是按决策问题重写。规则见 `references/audience-adaptation.md`。
- **阶段 2**：判断报告类型（咨询式 / 经营式 / 混合）→ 外部搜索决策 → 指标口径 → 方法 → 数据清单。产出《分析框架》+《数据需求清单》。
- **决策门 B**：按"目标类型 + 数据条件 + 交付约束"三列判断是否建模，**默认不建模**。产出《建模决策单》。
- **决策门 C**：将 `report.yml` + 框架 + 数据清单 + 建模决策单打包评审，未过回到阶段 2。
- **阶段 3-7**：数据准备与确认 → 外部信息+初步验证+大纲 → 文字版报告 v1.0 → 初稿评审 → PPT → 优化交付+复盘。详细指引在到达对应阶段时读取 `references/stage-3-7-details.md`。

### 产出物

按阶段对应模板（位于 `skills/analysis-report-builder/assets/templates/`）：

| 阶段 | 产出物 | 模板 |
|---|---|---|
| 0-1 | report.yml | report.yml |
| 2 | 分析框架 + 数据需求清单 | 01-分析框架与数据需求.md |
| 决策门B | 建模决策单 | 02-建模决策单.md |
| 3 | 数据差距说明 + 数据需求文件 + 数据质量报告 + 口径确认单 | 03/04/05 |
| 4 | 分析大纲 v0.5 | 06-分析大纲.md |
| 5 | 分析报告 v1.0 | 07-报告模板.md |
| 6 | PPT（按受众版本） | —（推荐配合 dashi-ppt-skill） |
| 7 | 复盘沉淀清单 | — |

### 使用约束

**交互约束**

1. **每阶段必须确认**：完成一个阶段后呈现产出物并暂停，等用户确认才进入下一阶段，不连续推进。
2. **随时可中断**：用户说"停""改需求""回到阶段X"立即响应并更新状态。
3. **断点续跑强制**：每完成一个产出物或子步骤立即更新 `_报告进度.md`；新会话必须先读取状态文件恢复现场。
4. **`_报告进度.md` 的模板由 `setup-anappt` 维护**：本 Skill 只读写该文件，不另存模板。

**质量约束（决策门）**

- **决策门 A**：受众决定后续每一步深度与语言，决策门 A 确认的语言规范在阶段 5/6 每章自查一次。
- **决策门 B（建模默认不做）**：除非"目标类型（预测/优化）+ 数据条件（样本足、标签可得）+ 交付约束（时间允许、可接受复杂度）"三列都满足，否则不上模型。决策单必须写明"不建模的风险"并交用户确认。常见误用：为显得高级而建模、样本不足硬做、把相关性当因果、跳过验证直接交付。若建模，强制执行"业务化翻译"——把系数/特征重要性/置信区间翻译成"哪些因素影响最大、影响多少、建议怎么调整"。
- **决策门 C**：框架评审未过回到阶段 2，明确记录修改点。
- **决策门 D**：初稿评审未过回到阶段 5。

**内容约束**

- **结论先行**：文字版报告与 PPT 均遵循金字塔结构，标题即结论。
- **受众适配**：一份结论按受众裁剪呈现，非做三份独立报告。管理层版按决策问题重写而非删减细节；篇幅、语言、证据强度、建模呈现、图表数量均按受众矩阵规范。
- **建议可执行**：每条建议指明"谁、做什么、何时、预期效果"。
- **数据可追溯**：每个数字回溯到阶段 3 数据快照，每个外部信息标注来源与时效。
- **合规红线**：`report.yml.compliance` 中 `cannot_quote` 与 `cannot_conclude` 字段定义的禁区全程不得违反。
- **复盘沉淀**：阶段 7 输出可复用模板、口径、踩坑清单，询问是否入库。

**参考文件加载时机**

- `references/methods-toolbox.md`——阶段 2 读取
- `references/audience-adaptation.md`——决策门 A 与阶段 5、6 读取
- `references/modeling-decision.md`——决策门 B 读取
- `references/stage-3-7-details.md`——阶段 3 开始时读取
- `references/report-writing-llm-spec.md`——阶段 5 读取

## 三、典型使用流程

```
1. 用户："初始化报告项目"
   → setup-anappt 创建目录、report.yml、_报告进度.md、data/，git 首次提交

2. 用户："做一份经营分析报告"
   → analysis-report-builder 检测到状态文件，进入阶段 0-1 grill 追问

3. 阶段 0-1：LLM 滚动提问 → 填充 report.yml → 用户确认锁定
   → 决策门 A：确认受众 → 阶段 2：框架与数据需求
   → 决策门 B：建模评估 → 决策门 C：框架评审
   → 阶段 3-5：数据 → 大纲 → 文字报告 v1.0
   → 决策门 D：初稿评审 → 阶段 6：PPT → 阶段 7：交付 + 复盘

4. 任意时刻可中断；新会话再次触发主 Skill 即从断点续跑
```

## 四、语言

默认简体中文。报告正文遵循"结论 + 影响 + 建议"表达顺序，少术语；管理层版术语带解释、数字有参照系。
