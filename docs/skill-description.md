# AnaPPTSkills 技能说明

AnaPPTSkills 是一套面向**经营 / 咨询分析报告**的 AI Agent 技能集，由三个相互配合的 Skill 组成。它们不是可执行程序，而是通过 `SKILL.md` 声明触发条件、交互原则与执行步骤，由 AI Agent（如 Trae、Claude Code）在对话中识别意图后按结构化流程推进。

| Skill | 角色 | 定位 |
|---|---|---|
| `setup-anappt` | 项目初始化 | 准备工作目录、锚定 git、生成首个 commit |
| `analysis-report-builder` | 报告构建主流程 | 按 7 阶段 + 4 决策门协作产出报告 |
| `review-report` | 整体审校 | 按风险定级跑五层审查 + 换眼复核，产出 `_审校报告.md` |

三者为"**建目录 → 产报告 → 做审校**"的接力关系：`setup-anappt` 建好目录与状态文件，`analysis-report-builder` 读取并推进流程，`review-report` 在交付后（或对任意已有报告）做独立复核，并把问题分级成优化队列驱动回改。

## 一、`setup-anappt`——项目初始化

### 触发条件

用户说出以下任意意图时触发：

- "初始化报告项目"
- "新建分析项目"
- "开始一个新的分析报告"
- 直接点名 "setup-anappt"

### 如何使用

在对话中直接表达上述意图即可，无需参数。也可附带目录名作为参数（在当前工作目录下创建子目录）。

Skill 会按以下 5 步执行：

1. **确认目录**：无参数则用当前工作目录；有参数则以参数名为子目录名创建。
2. **锚定 git（避免嵌套仓库）**：先执行 `git rev-parse --is-inside-work-tree` 判断当前目录是否已被某 git 仓库覆盖：
   - 已覆盖 → 不再 `git init`，沿用既有仓库；
   - 未覆盖 → 在目标目录执行 `git init`。
3. **创建目录结构与文件**：
   ```
   <目标目录>/
   ├── report.yml           ← 报告设定文件（阶段 0-1 填充并锁定）
   ├── _报告进度.md           ← 断点续跑状态文件
   └── data/                ← 用户数据文件目录（空）
   ```
   两个文件分别从 `skills/setup-anappt/assets/templates/` 复制，内容保持空字段待填。
4. **首次提交**：`git add report.yml _报告进度.md data/` 并 commit "chore: 初始化分析报告项目"。
5. **完成告知**：列出已创建文件、git 仓库状态、下一步（调用 `analysis-report-builder` 开始阶段 0-1）。

### 产出物

- `report.yml`：报告设定文件，包含 title / motivation / audience / objectives / success_criteria / delivery / scope / constraints / existing_materials / reader_context / compliance / benchmark 等字段，初始全空。
- `_报告进度.md`：断点续跑状态文件，含项目基本信息、当前进度、各阶段状态表、问题列表、关键决策记录、变更记录。
- `data/`：空目录，用于后续存放用户数据。

### 使用约束

- **不允许嵌套 init**：必须先检测是否已被 git 仓库覆盖，避免在已仓库内再 `git init` 产生嵌套。
- **模板内容保持不变**：复制 `report.yml` 与 `_报告进度.md` 时内容原样复制，所有字段留空，由阶段 0-1 填充，本 Skill 不预填任何字段。
- **完成条件严格校验**：三件产出物必须真实存在于目标目录；`git rev-parse --is-inside-work-tree` 在目标目录必须返回 `true`；`git log --oneline -1` 必须显示首条 commit。
- **本 Skill 只负责初始化**：不进入需求追问、不填充 `report.yml`、不创建报告内容文件——这些由 `analysis-report-builder` 负责。

## 二、`analysis-report-builder`——报告构建主流程

以"分析负责人 + 数据分析师"身份，与用户（业务对接人 + 质量评审人）协作，按阶段产出报告。

### 触发条件

用户说出以下任意意图时触发：

- "做一份分析报告"
- "经营分析""业务分析""专题分析""竞品分析"
- "按 SOP 走报告流程"
- "帮我逐步构建报告"
- 中断后继续已有报告流程时再次触发

### 如何使用

#### 前置检查

新会话开始时先检测 `_报告进度.md` 与 `report.yml`：

- **不存在** → 提示用户先调用 `setup-anappt`；
- **存在** → 读取后从断点继续，或按用户要求从指定阶段重做（重做时保留上游产出物，只覆盖该阶段及之后内容）。

#### 总体流程

```
阶段0-1 需求承接（grill 追问）→ report.yml
        ↓
【决策门A】受众分层与报告形态
        ↓
阶段2 分析框架与数据需求
    ├─ 判断报告类型 → 外部搜索决策 → 指标口径 → 方法选型 → 数据清单
    ↓
【决策门B】是否建模（默认不建模）→【决策门C】框架评审
        ↓
阶段3 数据准备与确认 → 阶段4 外部信息+初步验证+大纲（含配图规划）
        ↓
阶段5 文字版报告 v1.0 →【决策门D】初稿评审
        ↓
阶段6 PPT（图表重绘 + 报告↔PPT 对账）→ 阶段7 优化交付 + 复盘沉淀
```

每阶段统一执行 5 个动作：(1) 说明本阶段目标；(2) 按模板产出交付物；(3) 对照完成条件自查；(4) 呈现用户确认；(5) 更新 `_报告进度.md`。

#### 各阶段要点

- **阶段 0-1 需求承接**：用 grill 追问机制生成 3-5 个高优先级问题，逐题深挖，动态填充 `report.yml`。用户模糊时主动给出 2-3 个具体选项 + 推荐理由。终止条件为 `report.yml` 全字段填充且用户确认"可以锁定"。**4 问必答**：给谁看？为什么现在做？要什么结论？何时交付？答不出任一继续追问。
- **决策门 A**：确认主/次受众与报告形态。管理层版不是业务版删减版，而是按决策问题重写。规则见 `references/audience-adaptation.md`。
- **阶段 2**：判断报告类型（咨询式 / 经营式 / 混合）→ 外部搜索决策 → 指标口径 → 方法选型 → 数据清单。方法选型先答"五问法"（分析目标 / 业务问题域 / 数据条件 / 约束条件 / 要支撑的决策）再落方法，选定即写明该方法的前提条件与验证方式；**图表选型也在本阶段定型**——先写出要表达的相对关系，再定图表类型与编码通道。产出《分析框架》+《数据需求清单》。
- **决策门 B**：按"目标类型 + 数据条件 + 交付约束"三列判断是否建模，**默认不建模**。建模必须完成业务化翻译（系数/特征重要性/置信区间 → 哪些因素影响最大、影响多少、怎么调整）。产出《建模决策单》。
- **决策门 C**：将 `report.yml` + 框架 + 数据清单 + 建模决策单打包评审，未过回到阶段 2。
- **阶段 3**：数据差距评估 → 数据需求文件 → 数据质量报告与口径确认。质量问题逐项标"能用但打折"，口径须有用户签字确认记录，数据版本快照可复现。
- **阶段 4**：收集外部基准（每条标来源与时效）→ 用已有数据跑初步结果验证阶段 2 的假设（解读按事实→对比→解释→启示四层递进，无基准不下好坏判断）→ **立配图规划**（发现 → 要表达的关系 → 图表 → 编码通道）→ 写文字版大纲。产出《分析大纲 v0.5》。
- **阶段 5**：三步生成，禁止单次成稿——① 骨架继承与校验（必要结论覆盖矩阵、被推翻假设的下游结论已修正、参照系完备）；② 数字台账（每个数字可回溯到数据快照或外部信息清单，成文后逐项回查，台账外数字即幻觉信号）；③ 分章撰写 + 终稿通读（每章首行「本章重点」章眼，配图按"引出—读图—落点"图文互证）。产出《分析报告 v1.0》。
- **决策门 D**：以受众立场发起独立评审，只输出问题清单——存疑论断、数字/术语/逻辑不一致、无信息量的句子、断裂的章节、未被解读的配图，以及逐图挑出的图表误导性呈现；未过回到阶段 5 修订并记录版本变更。
- **阶段 6**：PPT 生成——一页一观点、标题即结论、图表重绘（不截图贴表）、每页配讲稿备注。渲染后先跑机器与样式校验，再由独立 subagent 以《分析报告 v1.0》为账本做**报告↔PPT 对账**（结论覆盖 / 章节覆盖 / 核心数字一致 / 禁区扫描），最多 2 轮，对账不过不交付。
- **阶段 7**：电梯测试（30 秒复述核心结论）→ 评审意见分"结论质疑 / 呈现意见"处理 → 输出复盘沉淀清单（可复用模板、口径、踩坑点）并询问是否入库。

#### 产出物

按阶段对应模板（位于 `skills/analysis-report-builder/assets/templates/`）：

| 阶段 | 产出物 | 模板 |
|---|---|---|
| 0-1 | report.yml | report.yml |
| 2 | 分析框架 + 数据需求清单 | 01-分析框架与数据需求.md |
| 决策门B | 建模决策单 | 02-建模决策单.md |
| 3 | 数据差距说明 + 数据需求文件 + 数据质量报告 + 口径确认单 | 03/04/05 |
| 4 | 分析大纲 v0.5（含配图规划） | 06-分析大纲.md |
| 5 | 分析报告 v1.0（含图表清单） | 07-报告模板.md |
| 6 | PPT（按受众版本） | —（推荐配合 dashi-ppt-skill） |
| 7 | 复盘沉淀清单 | — |

### 使用约束

**交互约束**

1. **每阶段必须确认**：完成一个阶段后呈现产出物并暂停，等用户确认才进入下一阶段，不连续推进。
2. **随时可中断**：用户说"停""改需求""回到阶段X"立即响应并更新状态。
3. **断点续跑强制**：每完成一个产出物或子步骤立即更新 `_报告进度.md`；新会话必须先读取状态文件恢复现场。
4. **`_报告进度.md` 的模板由 `setup-anappt` 维护**：本 Skill 只读写该文件，不另存模板。

**质量约束（决策门）**

- **决策门 A**：受众决定后续每一步深度与语言，决策门 A 确认的语言规范在阶段 5/6 每章自查一次。
- **决策门 B（建模默认不做）**：除非"目标类型（预测/优化）+ 数据条件（样本足、标签可得）+ 交付约束（时间允许、可接受复杂度）"三列都满足，否则不上模型。决策单必须写明"不建模的风险"并交用户确认。常见误用：为显得高级而建模、样本不足硬做、把相关性当因果、跳过验证直接交付。若建模，强制执行"业务化翻译"。
- **决策门 C**：框架评审未过回到阶段 2，明确记录修改点。
- **决策门 D**：初稿评审未过回到阶段 5；评审须覆盖配图的诚实性（比例、参照系、轴截断、3D、面积编码）。

**内容约束**

- **结论先行**：文字版报告与 PPT 均遵循金字塔结构，标题即结论；每章以加粗「本章重点」章眼承接前后，连读各章章眼即成故事线。
- **受众适配**：一份结论按受众裁剪呈现，非做三份独立报告。管理层版按决策问题重写而非删减细节；篇幅、语言、证据强度、建模呈现、图表数量均按受众矩阵规范。
- **图表信度**：配图遵循 `references/visualization-principles.md` 的"**信 · 达 · 雅**"三准则——信（比例守恒、比较自带参照系、不用设计替代数据）是第一道门槛，违信即废图；达（编码通道选在效率前排、数据墨水占比最大化、关键点直接标注）次之；雅（配色有语义、图题即结论、视图排序符合阅读顺序）再次。每张图交付前过逐图自检清单。
- **建议可执行**：每条建议指明"谁、做什么、何时、预期效果"。
- **数据可追溯**：每个数字回溯到阶段 3 数据快照，每个外部信息标注来源与时效。
- **合规红线**：`report.yml.compliance` 中 `cannot_quote` 与 `cannot_conclude` 字段定义的禁区全程不得违反（含附录、图表注释、讲稿备注）。
- **复盘沉淀**：阶段 7 输出可复用模板、口径、踩坑清单，询问是否入库。

| `analysis-model-selection-guide.md` | 阶段 2 | 分析手段选型（分析层次、统计检验、机器学习、归因方法） |
| `modeling-decision.md` | 决策门 B | 是否建模的判断表、风险与不建模理由写法 |

## 三、`review-report`——整体审校

### 触发条件

用户说出以下任意意图时触发：

- "review 这份报告""审校报告"
- "检查报告质量""报告体检"
- "文字和 PPT 一起查"
- 交付后想再做一轮独立复核时

### 如何使用

以**挑剔的评审人**身份复核整份报告。核心信条：**审的是结论—证据链，不是校对**——错别字与格式是最低价值的一层，真正决定质量的是每条结论有没有被数据扎实支撑。

```
定范围与定级 → 载入锚点 → 五层审查（文字 + PPT + 两者对齐）
        → 换眼复核（独立 subagent）→ 落盘 _审校报告.md → 优化回路
```

1. **定范围与定级**：确认审校对象（文字报告？PPT？两者？）与版本，并按 `report.yml` 用途判风险档位（内部草稿 / 内部决策 / 对外发布·财务合规·学术），据此决定本轮做到第几层。
2. **载入锚点**：交叉对齐 `report.yml`（成功标准 / 禁区 / scope / audience）、06 号大纲、05 号口径确认、数字台账、报告全文与 PPT 全量文案，作为"事实与口径的账本"。
3. **五层审查**：按优先级逐层过 `references/review-checklist.md`——
   - 硬伤：数据溯源、亲算校验、口径一致、**图表核对**（含比例守恒、轴截断、参照系、配色误导）、时效锚点；
   - 逻辑与结论：结论—证据对应、相关 vs 因果、反方视角、回扣原问题；
   - 完整与一致：选择性呈现、交叉引用、文字↔PPT 一致；
   - 受众与风险：受众适配、敏感与合规；
   - 形式：排版与表达。
   每个发现标 **必改 / 建议 / 可选**，记位置、依据锚点、修订动作与回退阶段。
4. **换眼复核**：派一个**不共享写作上下文**的独立 subagent 冷读全稿，以读者/审计立场只输出问题清单，破作者"补全盲区"。
5. **落盘 `_审校报告.md`**：总体判定 + 问题清单表 + 五层逐项结论 + 高频翻车点专项 + 换眼记录 + 按严重度排序的优化队列；多轮追加为"轮次 N"，不覆盖历史。
6. **优化回路**：按队列回到 `analysis-report-builder` 对应阶段修订（结论/证据回阶段 4–5，呈现/文字↔PPT 回阶段 6，形式回阶段 5/7），可重跑本技能进入新一轮，直到必改为零。

### 产出物

- `_审校报告.md`（模板位于 `skills/review-report/assets/templates/审校报告.md`）：问题分级清单 + 优化队列 + 轮次记录。

### 使用约束

- **不改稿，只审**：只输出问题与修订动作，重不重写由用户决定。
- **按风险定级**：内部草稿全套审会拖垮节奏，对外发布连形式层都不能省——先定档再定深度。
- **换眼破盲区**：关键一轮必须用未参与写作的独立视角复看。
- **规则不重定义**：判定标准以 `analysis-report-builder` 的规约为唯一出处（口径与数字格式见 `report-writing-llm-spec.md` 第七节，确定性三级见第四节，禁区见第一节，图文互证见第六节，图表信度见 `visualization-principles.md` 第一、六节），本清单只列"怎么查"。
- **断点友好**：多轮审校按轮次追加写入，重跑时读 `_报告进度.md` 定位最新报告版本。

## 四、典型使用流程

```
1. 用户："初始化报告项目"
   → setup-anappt 创建目录、report.yml、_报告进度.md、data/，git 首次提交

2. 用户："做一份经营分析报告"
   → analysis-report-builder 检测到状态文件，进入阶段 0-1 grill 追问

3. 阶段 0-1：LLM 滚动提问 → 填充 report.yml → 用户确认锁定
   → 决策门 A：确认受众 → 阶段 2：框架、方法选型与数据需求
   → 决策门 B：建模评估 → 决策门 C：框架评审
   → 阶段 3-4：数据准备 → 初步验证 → 配图规划 → 大纲
   → 阶段 5：文字报告 v1.0 → 决策门 D：初稿评审
   → 阶段 6：PPT（图表重绘 + 报告↔PPT 对账）→ 阶段 7：交付 + 复盘

4. 用户："review 这份报告"
   → review-report 定级 → 五层审查 → 换眼复核 → _审校报告.md
   → 按优化队列回 builder 对应阶段修订 → 重跑审校直到必改为零

5. 任意时刻可中断；新会话再次触发对应 Skill 即从断点续跑
```
