## 一、总体结构（先看这一张图）

```
阶段0 需求承接与受众确认 ──┐
阶段1 动机与需求（问题树） ├→【决策门A】受众分层与报告形态
阶段2 分析框架与数据需求 ──┘        ↓
        ↓
    【决策门B】是否需要建模？
        ├─ 是 → 2.5 建模子流程（模型设计/验证/业务化翻译）
        └─ 否 → 继续
        ↓
    【决策门C】框架评审（评审人签字，未过回到阶段2）
        ↓
阶段3 数据准备与确认
阶段4 外部信息 + 初步验证 → 大纲v0.5
阶段5 文字版报告 v1.0（含结论与建议）
        ↓
    【决策门D】初稿评审（未过回到阶段5）
        ↓
阶段6 PPT（按受众版本）
阶段7 优化与交付 + 复盘沉淀
```

三个关键设计说明：

1. **决策门B（建模）单独拉出来**——因为它不是阶段，而是"分析目标→方法"的映射决策，放阶段2之后最合适。判断标准在下面第三节。
2. **咨询分析和经营分析的区别不在流程，在阶段2的"分析框架"类型**：
   - 咨询式：框架驱动，外部视角（波特五力、价值链、对标分析），结论导向
   - 经营式：指标体系驱动，内部视角（漏斗、健康度、ABC分层），诊断导向
   - 两者共用同一套SOP，只是阶段2的方法工具箱不同——我建议在SOP里把两个工具箱并排列出，由分析负责人按目标选择。
3. **多受众不是"做三份报告"，而是"一份结论、针对性呈现"**。受众适配在第四节。

## 二、角色定义（SOP要先定人）

| 角色        | 职责             | 关键节点       |
| --------- | -------------- | ---------- |
| 分析负责人（PM） | 需求对接、框架决策、质量把控 | 决策门A/B/C/D |
| 数据分析师     | 数据、分析、建模执行     | 阶段3/4/5    |
| 业务对接人     | 提供数据、确认口径、验证发现 | 阶段3签字、决策门D |
| 质量评审人     | 中立评审，不参与执行     | 决策门C/D     |

> 小团队可以兼职，但"评审人"和"执行人"**不要是同一个人**，否则评审形同虚设。

## 三、每个阶段的SOP要素（产出物 + 验收标准 + 负责人）

### 阶段0-1：需求承接与动机需求

- **关键动作**：需求访谈用STAR法（背景/任务/期望动作/期望结果）；问题树拆解
- **产出物**：《需求简报》一页纸（题目、受众、决策场景、触发事件、期望形态、交付时间、边界）
- **验收标准**：能回答4问——**给谁看？为什么现在做？要什么结论？何时交付？** 答不出任何一问，不进入阶段2
- **负责人**：分析负责人 + 业务对接人

### 阶段2：分析框架与数据需求

- **关键动作**：选框架类型（咨询/经营/混合）→ 指标口径定义 → 方法选定 → 数据清单与可得性评估
- **产出物**：《分析框架》《数据需求清单》
- **验收标准**：每个子问题都有方法；每个方法都有数据支撑或明确的代理方案
- **负责人**：分析负责人（框架）、数据分析师（数据）

### 【决策门B】建模评估单

判断依据是**目标类型 + 数据条件 + 交付约束**，三列都要过：

| 判断维度 | 不需要建模                       | 需要建模                     |
| ---- | --------------------------- | ------------------------ |
| 目标类型 | 描述"是什么"、诊断"为什么"（对比/归因/漏斗可答） | 预测"会怎样"、优化"怎么做"          |
| 数据条件 | 样本不足、无标签、数据质量差              | 有效样本足够（分类/回归一般≥几百条）、标签可得 |
| 交付约束 | 时间紧、管理层要求强可解释               | 时间允许、结论用于内部决策可接受模型复杂度    |

**产出物**：《建模决策单》（是否建模、模型类型、理由、不建模的风险）。**决策单要签字**，防止事后"当时为什么没建模"的争议。

⚠️ 一个反对意见：**建模不是加分项**。多数经营分析问题用描述统计+对比+归因就够，硬上模型反而拉长周期、降低可解释性。决策单里应该默认选项是"不建模，除非有明确理由"。

如果建模，进入**2.5 建模子流程**，并强制要求最后一步是"**业务化翻译**"：模型系数、特征重要性、置信区间对管理层没有意义，必须翻译成"哪些因素影响最大、影响多少、建议怎么调整"。你数学背景应该很清楚：很多团队死在"模型做出来了，老板看不懂，结论落不了地"。

### 阶段3：数据准备与确认

- **关键动作**：数据字典核对、清洗留痕、口径确认、质量报告
- **产出物**：《数据质量报告》《口径确认单》
- **验收标准**：质量问题有清单且标注"能用但打折"；**口径有业务方签字**；数据版本快照可复现
- **负责人**：数据分析师执行，业务对接人签字

### 阶段4：外部信息 + 初步验证 + 大纲

- **关键动作**：外部基准收集（每条标注来源与时效）、**用已有数据跑一轮初步结果验证阶段2的假设**、写大纲
- **产出物**：《分析大纲v0.5》（含外部信息清单与局限声明）
- **验收标准**：每个发现都有参照系；假设要么被初步验证、要么被推翻并修正
- **负责人**：数据分析师

### 阶段5：文字版报告

- **关键动作**：结论先行（金字塔结构）、图表三要素（标题/结论/来源）、数字一致性校对、每个发现后接"对决策的含义"、**结论与建议独立成章**
- **产出物**：《分析报告v1.0》
- **验收标准**：管理层版附一页纸摘要；建议可执行（谁、做什么、何时、预期效果）；数据来源可追溯
- **负责人**：分析负责人（质量）、数据分析师（执行）

### 阶段6：PPT + 阶段7：优化交付

- **PPT**：一页一观点、标题即结论、图表重绘、讲稿备注、按受众选版本（页数：决策场景10-20页）
- **优化交付**：电梯测试（不熟悉的人30秒复述核心结论）、评审意见分"结论质疑/呈现意见"两类处理、版本与变更记录、**复盘沉淀**（模板、口径库、踩坑清单入库）

## 四、受众适配矩阵（你特别提到的，重点）

同一个分析，按最终读者裁剪。**阶段0就要确认主受众和次受众**，因为它决定后面每一步的深度和语言。

| 维度   | 管理层              | 业务人员          | 外部人员              |
| ---- | ---------------- | ------------- | ----------------- |
| 核心诉求 | 决策依据             | 操作指引          | 可信度 / 合规          |
| 篇幅   | 报告≤15页 + 一页纸摘要   | 详细版 + 分场景操作建议 | 完整版 + 附录          |
| 语言   | 结论 + 影响 + 建议，少术语 | 结合业务场景，术语带解释  | 中立客观，方法透明         |
| 证据强度 | 关键证据 + 风险提示      | 详细数据 + 操作步骤   | 全部来源 + 方法论 + 局限声明 |
| 建模呈现 | 结论 + 置信度，不展开技术   | 模型怎么用于工作      | 技术细节 + 验证过程       |
| 图表   | 1-2张核心图，标结论      | 分场景图表         | 完整图表 + 附录         |

最终的受众适配，需要按照不同的需求，在PPT中有针对性的呈现。

## 五、落地建议（SOP要能执行，不是文档）

1. **每个产出物配模板**：《需求简报》《建模决策单》《质量报告》《大纲》《报告》《PPT》，入库共享
2. **评审会固定30分钟**：决策门C（框架评审）+ 决策门D（初稿评审），两次评审是SOP的"刹车"，也是质量下限
3. **先跑试点**：选1-2个项目完整走一遍SOP，把模板和决策单打磨后再全员铺开——直接铺文档大概率变摆设
4. **SOP本身要设更新机制**：每季度复盘一次，把"踩过的坑"补进模板和决策单

## 信息分级说明

- 【事实】CRISP-DM、金字塔原理、STAR访谈法、咨询框架（波特五力等）均为成熟方法论，可查证
- 【推测】建模样本量"几百条"是行业经验值，具体取决于问题复杂度与模型类型，需按项目评估
- 【观点】"建模默认不做，除非有明确理由""评审人与执行人必须分离"是我的立场，理由是防止决策单流于形式
